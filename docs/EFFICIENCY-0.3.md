# DSH Soul 0.3：让经验可检验

目标优先级是结果正确、少返工、短完成时间；费用作为可调整限制。较强模型如果能少走弯路，可以比便宜模型更有效率。本版没有根据任务难度自动选择模型，后台学习仍使用用户显式配置的路由。

## 架构

```text
用户偏好/项目事实 ──────────→ 有界上下文
                              ↑
技能候选 → 用户接受 → trial → 正常任务使用 → 来源与运行指标
                       ↑                         ↓
                 新版方法候选 ← 经验提炼 ← 带限制的结果报告
                                                 ↓
                                          人工判断改进/损害
                                                 ↓
                               两个不同会话通过 → active
                                                 ↓
                                   相关技能中优先召回
```

偏好与技能采用不同准入条件。候选不能替代当前用户指令；试用技能保留条件、检查与反例。质量有问题的方法即使耗时短也不能自动获胜。

`runs` 存单轮观察，`run_calls` 用真实 call ID 配对工具事件，`trials` 存方法、目标、基线和评价，`trial_sources` 存报告引用的实际来源。模型不能提交或覆盖耗时、步骤数和工具错误数。模型报告与人工审核是独立字段。

`learning_trial` 在真正使用方法之前登记并同时返回全文；随后正常执行任务。`learning_evidence` 获取来源 ID，`learning_result` 提交最多 8 条本轮来源。首轮可保存 uncertain 报告；后续在相同项目、同目标时可引用已完成报告作为基线。没有条件可比性时应保留 uncertain，不能为了让比较通过而伪造目标或重做有副作用的操作。

已有 `/learn feedback` 表示人工确认单次使用通过；`/learn assess helped` 更严格，还要求可比较的完整记录。两者按 session 合并计数，不能对同一会话重复加分。活跃技能按相关程度筛选后，才以人工通过会话和已确认改进等证据排序；事实和偏好位置不被技能评分挤占。

## 效率取舍

- 不在每个任务前启动多个代理或候选执行；仅观察实际发生的正常任务。
- 登记返回完整技能，避免同一流程先 get 再 trial 的重复读取。
- 复用本地检索缓存，只有相关方法进入上下文；不注入整个经验库。
- 反思采用空闲时增量提炼，明确纠正、失败或手动 review 才排队；不逐轮调用独立模型。
- efficiency 提供更充足的输入和输出额度，避免必要条件与检查被挤掉；economy 与显式数值覆盖仍可用。额度是上限，不是使用目标。

每次方法试用增加主模型工具轮次，可能让简单任务更慢。因此工作流是按需使用；本版本不声称净加速。现有本地基准只能测检索和记录开销，真实效率需要在代表性任务上评估成功率、完整任务耗时、人工修正次数和总 token。

## 证据边界

报告需要当前会话、当前项目、所登记轮次的用户或工具来源。Soul 自身工具输出不作为独立成功观察；用户的任务要求本身也不是成功证明，人工仍须核对证据是否证明目标完成。缺基线、缺报告、缺来源、未结束、不完整、执行后登记或一轮多方法均阻止确认改进归因。

比较值为两轮原始观察差，不是因果估计。步骤数不是推理质量，工具错误不是返工计数，执行结束不是任务成功。即使字段符合要求，同目标字符串也无法保证任务难度、环境、模型等一致。本版不测跨轮任务总时间，不测独立模型的额外时延对完整工作流的净影响。

修改或遗忘证据会递归清除依赖它的比较贡献；由相关运行来源提炼的新记忆保留父技能依赖。遗忘技能连同尚未报告的关联观察也会抑制，防止重新学习。运行指标去重、设上限；工具结果缺失、时钟倒退、插件关闭或重启丢失观察时段不会被当作完整成功记录。

## Harness² 的借鉴范围

参考 Google Research 官方仓库 https://github.com/google-research/harness2 及论文 https://arxiv.org/abs/2610.14224 。核对日期：2026-10-26；阅读时主分支版本 `1cfe254e8d25b15f37048c3730134686abe60335`。

Harness² 的 Propose–Probe–Compose 用执行对比改进当前任务的运行框架，再将证据支持的经验用于后续任务。Soul 借鉴“方法变化、行为观察、改进归因、跨任务经验分开记录”的思路，采用已有正常任务的观察建立轻量基础。

未移植其完整递归执行器、候选并行探测、框架代码编辑或模型基准。实现独立编写，未复制上游代码，也不套用论文提升数字。以后若加入自动探测，需要单独设计可重放任务、无副作用的验证器、终止条件及整体时延评测，不能把当前报告流程宣传为已完成这些能力。
